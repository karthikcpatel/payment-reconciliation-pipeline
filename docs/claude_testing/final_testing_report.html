3. Architecture summary

Raw gateway and bank CSVs (no shared ID) → staging casts → merchant crosswalk (edit distance + 60 manual corrections) → candidate join → rank/tie typing → mart_reconciliation → mart_review_queue (+ CSV exports for Tableau).

4. Source-to-target data flow

gateway_transactions.csv -> stg_gateway_transactions --------\
bank_settlements.csv     -> stg_bank_settlements -> int_discovered_merchant_crosswalk -> int_final_merchant_crosswalk (+ seed)
                                                          \-> int_candidate_matches -> int_match_selection
                                                                 -> mart_reconciliation -> mart_review_queue -> data/mart_*_export.csv

5. Reconciliation model

Gateway-driven, single-stage, rule-based; tolerance + time-window; one chosen settlement per transaction but no exclusivity across transactions. Precedence: missing → ambiguous → duplicate → amount_mismatch (>0.01) → delayed (>3 calendar days) → matched.

6. Matching-rule summary

RuleValue
Merchantexact on crosswalk-resolved merchant
Amount|gateway−settled| ≤ greatest($5.00, 5% of gateway)
Windowtxn_ts ≤ settlement_date ≤ txn_ts + 15 days (inclusive)
Rankamount_diff asc, days_to_settle asc (no final tiebreaker)
Tiestop-2 equal amount_diff → duplicate (same amount+date) else ambiguous
Confidence1 unique; 2–4 medium; ≥5 low

16. Risks and limitations

  • 14 pre-existing dbt tests via `dbt test` (dbt not installed, no BigQuery project/credentials) — their logic was re-executed as equivalent SQL (CT009 ×4, CT010 ×10): all passed, but that is not a dbt run
  • load_to_bigquery.py, export_for_*.py, validate_*.py, spot_check/compare/measure/check/review scripts (BigQuery credentials)
  • Private ground-truth validations (files git-ignored, absent); README accuracy figures not verifiable
  • Exit-code, rollback, checkpoint, output-write-failure tests (no writers/services exist in repo or need BigQuery)
  • Local engine is DuckDB via sqlglot, not BigQuery.
  • Skills/agents: files validated; all 6 skills and 7 agents later appeared in the session's loaded lists (observed, not command-verified).
  • Mutation run predates review-driven test additions.

Assumptions needing confirmation

  • A1 a settlement should satisfy at most one transaction
  • A2 negative settlements are invalid
  • A3 non-'completed' statuses should (not) be reconciled
  • A4 a 1-cent difference is 'matched' by design
  • A5 tie-breaks must be deterministic
  • A6 bank-side orphans must be reported
  • A7 amount_mismatch should outrank delayed

17. Recommended fixes

  1. Deterministic tiebreaker (settlement_id) — PAYREC-004.
  2. One-to-one assignment — PAYREC-001.
  3. Test non-negativity on staging; define negative-amount handling — PAYREC-002.
  4. Unmatched-settlement model — PAYREC-003.
  5. Run IDs, timestamps, rule codes, run summary.
  6. Credential handling, README, orphan model hygiene — PAYREC-005..008.

20. Conclusion

The pipeline classifies and ranks as documented at the boundaries tested (119 checks pass, categories reproduce the BigQuery export exactly), but its reconciliation is not one-to-one, so matched volumes and settlement-level outputs cannot be trusted as a control until PAYREC-001 and PAYREC-004 are resolved. Nothing was run against BigQuery.
